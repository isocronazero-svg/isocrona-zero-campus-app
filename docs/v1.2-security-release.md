# V1.2 — revisión de seguridad y publicación

Fecha: 5 de noviembre de 2026. Rama de trabajo: `feature/v1.2`. Publicación: PR #336 hacia `main`.

## Correcciones

- **P1, sobrescritura durante el correo de recuperación:** #337 recarga el estado después del envío. La regresión añadida en #338 comprueba cursos, pagos y credenciales concurrentes. Se aplica la misma regla tras esperar la actualización PostgreSQL.
- **P2, reutilización simultánea del enlace:** #338 reclama el token con un UPDATE condicional de SQLite antes de cualquier espera. Solo una solicitud obtiene el permiso de actualizar. El token sigue consumido si falla PostgreSQL y después de reiniciar. El usuario debe solicitar otro enlace tras un fallo.
- **P1, JWT que recupera su validez al reiniciar:** los JWT se vinculan mediante HMAC a la credencial salada persistida en PostgreSQL. Cada escritura de contraseña cambia esa vinculación, aunque los tokens se emitan en el mismo segundo. No se depende del reloj ni de mapas en memoria. Las respuestas de usuario no incluyen hashes ni la versión interna.
- Los guardas de bearer, las cookies de cuentas PostgreSQL y `/api/session` verifican esa vinculación. El login clásico también consulta la credencial PostgreSQL, evitando reusar una copia local antigua. El cambio de contraseña propio, el administrativo y el restablecimiento de acceso del socio actualizan PostgreSQL. Las escrituras locales aisladas de contraseñas de cuentas PostgreSQL se rechazan: deben hacerse desde usuarios o recuperación.
- `updateUser` modifica únicamente los campos solicitados; una edición de perfil concurrente no puede restaurar el hash anterior. El cambio de contraseña propio añade una condición sobre la credencial autenticada para rechazar cambios concurrentes.
- `public/join.html` conserva el aviso bancario de `main`, con comprobación automática.

## Compatibilidad y operación

No hay migración de esquema ni modificación de datos reales. La vinculación usa el hash ya persistido y la clave JWT ya configurada. Los JWT anteriores a este cambio no contienen la vinculación y se rechazan: los usuarios PostgreSQL deben iniciar sesión de nuevo. Las sesiones recordadas anteriores de cuentas PostgreSQL también requieren login. Las cuentas exclusivamente locales mantienen su funcionamiento.

Una operación que atraviesa PostgreSQL y SQLite no es una transacción distribuida. Si falla la persistencia local después de cambiar PostgreSQL, se falla de forma cerrada, se conserva el token consumido y se debe solicitar otro enlace. No se intenta restaurar una contraseña antigua.
