# V1.1 · Seguridad del entorno QA

## Objetivo

El entorno QA de V1.1 debe poder probar la aplicación sin usar datos personales reales, credenciales de producción ni correo real.

## Reglas obligatorias

1. El servicio QA no debe compartir volumen, base de datos ni credenciales con producción.
2. Mientras existan credenciales demo conocidas, el QA no debe tener dominio público.
3. Cuando se vuelva a exponer el QA, debe arrancar con `NODE_ENV=production` y una cuenta administrativa bootstrap configurada mediante variables secretas de Railway, nunca escrita en GitHub.
4. El seed recomendado para un volumen QA nuevo o reseteado es `data/qa-private-seed.json` mediante:
   - `IZ_DEFAULT_STATE_PATH=/app/data/qa-private-seed.json`
5. El seed QA no contiene cuentas, contraseñas, socios ni solicitudes reales.
6. `IZ_EMAIL_ENABLED=false` durante todo el QA salvo una prueba de correo explícita y controlada.
7. Las cuentas QA deben usar nombres tipo `Admin QA Carlos`, `Admin QA Santi`, `Tesorería QA`, `Socio QA 01` y correos bajo `example.test` o un dominio de pruebas controlado.
8. Nunca reutilizar contraseñas del portal productivo.
9. Al terminar las pruebas, eliminar las cuentas QA o rotar las credenciales antes de cualquier nueva exposición pública.

## Preparación para volver a exponer QA

### Politica central de fixtures (#299)

`server/fixture-account-policy.js` toma las identidades de accounts/members y
las contrasenas publicas de `data/default-state.json`. Este archivo es un
fixture sintetico para CI/desarrollo, no un seed para QA expuesto. El catalogo
no depende de `IZ_DEFAULT_STATE_PATH` ni del estado editable del servidor.

- En test/development se conserva el comportamiento de los fixtures.
- En production se deniegan las identidades fixture independientemente de su
  rol, mayusculas o contrasena actual. Tambien se deniegan sus contrasenas
  publicas aunque se cambie el email, incluyendo hashes SHA256 y scrypt
  legacy/PostgreSQL. No se bloquean dominios completos ni IDs historicos.
- Se aplica tanto al login SQLite/JSON como a PostgreSQL, a la emision de
  cookies y a la lectura de sesiones temporales, recordadas y bearer existentes.
  El control no elimina cuentas ni migra datos.
- El bootstrap valido sigue usando las tres variables privadas existentes:
  email, password y name. Rechaza identidad/contrasena fixture sin imprimir
  valores. Puede reutilizar el ID historico del admin convertido por bootstrap.
- `IZ_ALLOW_DEMO_ADMIN_IN_PRODUCTION=true` conserva unicamente el bypass de
  ARRANQUE para emergencia. Nunca habilita autenticacion fixture. La ruta de
  recuperacion tampoco puede reabrir una identidad/contrasena fixture.

Regresion: `node scripts/check-fixture-account-policy.mjs`, integrada en
`check:app`. Cubre login HTTP de todos los fixtures y de instructor, reinicio
test/development -> production con cookie recordada real en SQLite, sesiones
en memoria, bearer/PostgreSQL (transporte simulado sin base remota), hashes de
credenciales renombradas, bootstrap valido/invalido, ausencia de secretos en
logs y conservacion de datos. Los secretos de prueba se generan al ejecutar.

Antes de generar un nuevo dominio público:

1. Configurar `IZ_DEFAULT_STATE_PATH=/app/data/qa-private-seed.json`.
2. Configurar `NODE_ENV=production`.
3. Configurar en Railway, como secretos, `IZ_BOOTSTRAP_ADMIN_EMAIL`, `IZ_BOOTSTRAP_ADMIN_PASSWORD` e `IZ_BOOTSTRAP_ADMIN_NAME`.
4. Confirmar `IZ_EMAIL_ENABLED=false`.
5. Resetear/recrear exclusivamente el estado del QA si se quiere partir del seed limpio. No tocar el volumen productivo.
6. Arrancar y confirmar `/healthz`.
7. Crear desde el admin QA las cuentas temporales adicionales necesarias.
8. Generar dominio público solo después de comprobar que las credenciales demo no permiten iniciar sesión.

## QA funcional mínimo

- Dos administradores simultáneos: cada uno debe comenzar en su propio perfil y mantener su contexto aislado.
- Tesorero: solicitud de justificante, visor online, validación e ingreso en libro interno.
- Socio: recepción del aviso, subida de justificante y acceso al canal de WhatsApp cuando se configure.
- Alta octubre-diciembre: año de cuota siguiente.
- Precio socio/no socio y snapshot del importe aplicado.
- Auditoría: actor, fecha, acción y entidad.
- Previsualización de diploma sin emisión real.
- Recarga y reinicio: persistencia QA.

## Nota sobre el repositorio público

`data/default-state.json` y varios scripts históricos contienen fixtures de demostración que son públicos por diseño y se usan en regresiones. No deben tratarse como credenciales privadas. La V1.1 debe reforzar que ninguna identidad/contraseña demo pueda autenticarse en un entorno productivo o QA expuesto. Si algún dato de los fixtures hubiese sido alguna vez real, debe rotarse/eliminarse fuera de GitHub; borrar el texto del último commit no elimina el historial Git.
