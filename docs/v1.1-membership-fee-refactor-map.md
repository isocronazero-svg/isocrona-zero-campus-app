# V1.1 · mapa técnico del refactor de cuota (#296)

## Objetivo

Aplicar una única política de **ejercicio efectivo de cuota** a todas las decisiones de backend.

Regla de negocio:

- alta nueva entre 1/10 y 31/12 (Europe/Madrid) → la cuota corresponde al año siguiente;
- durante los meses restantes del año de alta, el socio está activo y no debe quedar limitado ni recibir recordatorios del año natural de alta;
- al llegar el año cubierto, la misma cuota sigue siendo válida;
- al superar ese ejercicio, vuelve a prevalecer el año natural (ej.: alta noviembre 2026 / cuota 2027 → en 2028 se revisa 2028).

La política base está implementada en `server/membership-fee-policy.js` y cubierta por `scripts/check-membership-fee-policy.mjs`.

## API de política preparada

- `effectiveMembershipFeeYear(associate, date)`
- `associateFeeGapForDate(associate, date)`
- `isAssociateAccessLimitedByFee(associate, date)`
- `autumnMembershipBenefit(associate)`

No se debe replicar de nuevo la regla de octubre-diciembre en `server.js`.

## Puntos legacy localizados en `server.js`

### 1. Restricción de acceso

Actual:

`getAssociateCurrentYearQuotaGap()` obtiene `new Date().getFullYear()` y consulta `yearlyFees[año natural]`.

Cambio esperado:

- delegar el cálculo en `associateFeeGapForDate(associate)`;
- `isAssociateAccessLimitedByQuota()` debe usar esa misma política.

Resultado esperado: una alta de noviembre de 2026 con cuota 2027 pagada tiene gap 0 y acceso normal durante noviembre-diciembre de 2026.

### 2. Cierre/revisión administrativa del socio

Se han localizado varios recalculados de estado con:

`getAssociateYearFeeGap(associate, String(new Date().getFullYear()))`

Afectan a cierres/revisiones y transiciones hacia `Activa` / `Pendiente cuota`.

Cambio esperado:

- sustituir el año natural por el ejercicio efectivo;
- preferiblemente usar `associateFeeGapForDate()` para no duplicar la decisión temporal.

### 3. Recalculo general de estado

Existe otro bloque que, salvo estados especiales (`Baja`, `Revisar documentacion`, etc.), recalcula el estado con el año natural.

Cambio esperado:

- misma política central;
- una alta bonificada con cuota del año siguiente pagada debe permanecer `Activa`.

### 4. Automatización de cuotas

`runAutomationEngine()` define un `currentYear` global con el año natural y crea items `associate_fee` / recordatorios usando ese ejercicio.

Cambio esperado:

- resolver el ejercicio **por socio**, no una vez de forma global;
- usar `effectiveMembershipFeeYear(associate, now)` y `associateFeeGapForDate(associate, now)`;
- las claves/idempotencia de automatización que incluyan año deben utilizar el ejercicio efectivo;
- una alta bonificada 2026→2027 no debe generar item ni recordatorio de cuota 2026 si 2027 está pagada.

### 5. Recordatorio individual de cuota

El flujo individual también calcula `currentYear` con el año natural antes de `getAssociateYearFeeGap()`.

Cambio esperado:

- usar ejercicio efectivo y gap central;
- asunto/concepto del correo o notificación debe mostrar el ejercicio realmente reclamado.

### 6. Alta desde `Hazte socio`

La creación desde solicitud web contiene actualmente una inicialización hardcodeada equivalente a:

```js
yearlyFees: {
  "2024": 0,
  "2025": 0,
  "2026": annualBase,
  "2027": 0
}
```

Este es un bloqueante para octubre-diciembre.

Cambio esperado:

- calcular `membershipFeeYear` en el momento de crear/aprobar el socio, usando Europe/Madrid;
- imputar `annualBase` únicamente a ese ejercicio;
- mantener los años históricos requeridos por compatibilidad, pero no marcar el año bonificado como pagado de forma ficticia;
- no esperar a una reconciliación posterior para corregir el ejercicio: la ficha debe nacer coherente.

### 7. Registro económico

`createAssociatePaymentRecord()` ya recibe un `year` explícito. Los flujos que generan pagos automáticos o desde recordatorios deben pasar el ejercicio efectivo.

No se debe crear una segunda cuota/pago artificial para el año de alta bonificado.

El libro interno de ingresos debe seguir mostrando una sola entrada en el ejercicio real (`Cuota 2027` en el ejemplo).

## Regresiones ya preparadas

`check-membership-fee-policy.mjs` cubre:

- alta septiembre 2026 → ejercicio 2026;
- alta noviembre 2026 + cuota 2027 pagada → ejercicio efectivo 2027 y gap 0 durante 2026;
- enero 2027 → sigue ejercicio 2027 y gap 0;
- enero 2028 → ejercicio 2028 y vuelve a existir deuda si no se ha pagado;
- alta noviembre con cuota 2027 no pagada → deuda correcta;
- una corrección futura fuera del patrón octubre-diciembre no salta automáticamente el año natural.

## Regresiones que faltan al cablear `server.js`

- alta web 30/09/2026 → cuota 2026;
- altas web 01/10, 15/11 y 31/12 → cuota 2027;
- estado `Activa` y acceso no limitado durante 2026 si 2027 está pagada;
- cero recordatorios/items de cuota 2026 para esas altas;
- 01/01/2027 → cuota 2027 normal;
- 2028 → revisión 2028;
- un solo movimiento económico, sin falsa cuota 2026;
- bienvenida muestra la bonificación solo cuando corresponde.

## Límite de seguridad

No integrar V1.1 en `main` ni abrir el QA al público hasta que el cableado de `server.js` pase `npm run check:app`, smoke y QA real.
